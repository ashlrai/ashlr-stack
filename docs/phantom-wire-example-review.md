# Review questions for a Phantom wire webhook example

Use these questions to review the example generated by
[`phantom-wire.ts`](../packages/core/src/ai/phantom-wire.ts), not to approve it
for deployment. For a Stripe provider, wiring writes the fully commented file
`.stack/webhooks/stripe.ts`; it does not register a route or deploy a handler.
Wiring overwrites an existing file at that path. The example is a starting point,
not a production-ready handler.

## Input and claimed boundary

The example handler takes a `Request`. Its `stripe-signature` header and body
come from the caller; either can be forged. If uncommented as written, the
handler returns 400 for a missing or empty header, reads the body with
`req.text()`, and returns `ok`/200 for any non-empty header if the read
succeeds. A body-read failure rejects the handler. The header check establishes
only that a value was supplied, not the sender's identity or the body's
integrity. Reading text does not by itself establish that the exact raw bytes
required for verification have been preserved.

- Who can send this request, and which parts of its headers and body are
  attacker-controlled before authentication?
- What does a non-empty `stripe-signature` actually prove here, and where would
  the boundary lie between untrusted input and a verified event?
- If this example were uncommented unchanged, what happens to a forged request
  with a non-empty header, and could a 200 response be mistaken for verification?

## Unfinished verification

The generated `TODO(security)` says signature verification is **not
implemented**. The example does not retrieve the secret or compare the
signature; its provider-specific hint is a comment, not a verifier. The separate
vault inventory checks catalog secret names, not values or their suitability;
the webhook secret named in the example need not be a catalog secret checked
by wiring. Until verification succeeds, the body remains unauthenticated,
attacker-controlled input.

- Which current provider and webhook product documentation defines the exact
  raw payload, signing secret, headers, and verification procedure for this
  endpoint, and how will those inputs be preserved and obtained securely?
- Where will verification occur before parsing, trusting, or acting on the body,
  and how will missing or invalid signatures, unavailable secrets, and body-read
  failures be rejected?
- Which timestamp tolerance or replay protections apply to this provider and
  product, and how will they be enforced? Will a supported verifier be used, or
  will a direct MAC comparison be constant-time?
- What tests demonstrate acceptance of valid requests and rejection of forged
  signatures, changed bodies, missing headers, and applicable stale or replayed
  requests before any side effects?

These questions also apply to the Clerk, Supabase, and GitHub examples, but
header names and verification requirements differ. Confirm the scheme for the
specific product rather than inferring it from a generated hint. The recipe is a
separate input: manifests are unsigned, and catalog name checks do not establish
origin or integrity. Use recipes from a trusted source. See the
[reading guide](phantom-wire-example-reading-guide.md) for the generated steps
and the [broader review questions](phantom-wire-review-questions.md) for wiring
and failure handling.
