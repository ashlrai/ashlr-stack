# Site changelog review

Use this checklist when reviewing a change to the [site changelog](../packages/site/src/data/CHANGELOG.md), including changes copied from the [root changelog](../CHANGELOG.md). The root file is the source: the site's `sync-content` script copies it into the site package before development and builds. Edit the root entry first, then run `bun run --cwd packages/site sync-content` from the repository root and review the resulting diff. Check the diff even if the command succeeds; the copy script tolerates a missing source file.

- [ ] **Heading order:** Keep `# Changelog` first, `## Unreleased` before released versions, and released versions newest first. Check the version and date against the root entry. Use `###` for subsections under the appropriate release; keep any deeper headings nested without skipping levels. Existing historical heading styles need not be rewritten.
- [ ] **Readable formatting:** Review the rendered `/docs/changelog` page (for example, with `bun run --cwd packages/site dev`). Check that headings, paragraphs, lists, links, inline code, and fenced examples render as intended, with no broken nesting, unclosed fences, or accidental headings. Make long or technical entries understandable and preserve qualifications and user actions.
- [ ] **Compare with the root entry:** Find the corresponding `Unreleased` or version section in the root changelog and compare the complete entry, including examples, links, dates, and caveats. The site file should match the root file exactly; correct discrepancies in the root and sync again. Do not infer that a version is published merely because it appears in source.
- [ ] **Verify:** Run `diff -u CHANGELOG.md packages/site/src/data/CHANGELOG.md` and `HOME=$(mktemp -d) bun test packages/site/tests/changelog.test.ts` from the repository root. Resolve any difference or failing test, then repeat the review after further edits. Automated checks complement the rendered and editorial review.
