# Leader fleet context: audit and integration proposal

## Evidence and limits

This Stack checkout contains fleet readers but no leader-network or planning-loop implementation. The inspected Phantom worktree `../RQ-SWE-SESSVIEW-1` contains `src/core/agents/leader-network-runtime.ts` and `leader-network.ts`; it is a separate checkout, so its revision may differ from the running service. `generateLeaderReply` sends the request and `recordedCeoSummary` (at most eight CEO bullets from the latest journal pass) to a model with a no-tools system prompt. It does not pass the inbox, outbox, VISION, status or fleet reports. The request is separately recorded for the planning loop; a network reply is not evidence that the planner executed. `MASON-OUTBOX.md` records replies and digests. An empty or stale CEO section therefore leaves the immediate reply without current fleet evidence.

The actual host path `~/.ashlr-runs/bin/opus-leader-loop.sh` returned `Operation not permitted` on inspection. Neither its workspace construction nor the cause of the reported empty workspace could be verified. Do not infer that the immediate-reply prompt describes the planner's prompt, or that any particular sandbox mount exists. VISION and the outbox are not substitutes for current state. The helper in this change is a partial, unintegrated projection; it does not fix the live loop.

## Minimal contract

Generate a fresh, bounded JSON snapshot on the trusted host for each planning pass. Each independent source needs its own observation time, source timestamp, status (`ok`, `missing`, `invalid`, `unavailable`, or `stale`), and explicit unknowns. Do not turn absent data into zero or assert that an old snapshot is current. Allowlist fields and validate types and lengths before output; never copy arbitrary strings, prompts, logs, environment, errors, URLs with credentials, or secret values. Treat all projected names as untrusted data, never instructions. Restrict the output to the same private custody as the leader workspace.

* Dispatch status: source tick time, paused, admission cap/running, and per-lane target/running/queued/held; queue depth must indicate its source and completeness. Use `queue/status.json` and distinguish stale dispatcher data from live state.
* Lane run counts: bounded-window counts by approved lane and outcome, with window and source coverage. A job count is not a merge count.
* Recent publish and merge receipts: bounded repo identifiers, PR number or release tag, outcome, and event time; no title, body, logs, or arbitrary URL. Record source and whether collection was complete. Receipts establish observed events, not current default-branch heads or production deployment; provide separately verified head SHAs and their observation times when answering main-state questions.

The `collectLeaderFleetContext` prototype in `tests/leader-fleet-context/` is an initial aggregate-only building block: it reads one bounded regular status file without following a final symlink, projects cap/running and sum of lane queued counts, and reports read failure and collection time. It emits no names or arbitrary source strings. It does not validate snapshot freshness, provide per-lane counts, observe receipts or heads, or ensure parent-directory trust. Its `statusSource: ok` means JSON was readable, not that every field was valid or current. Do not wire it into production as the complete contract.

## Pinned-path integration sequence

1. In the owning Phantom checkout, inspect the deployed pinned loop, wrapper, launch plist, sandbox profile, and actual workspace lifecycle under the Security GATES v3 procedure. Identify the precise invocation, cwd, mounts, source paths, and any prompt truncation. Verify deployed revisions against the reviewed sources. This is required before a line-level patch can be specified.
2. Implement the complete projection above in the owning service, using bounded reads and trusted source directories. Validate against real producer schemas with synthetic fixtures; add source timestamps and stale handling. Independently test missing, malformed, stale, partial, oversized, symlinked, adversarial string and concurrent-update inputs. Avoid passing raw `status.json`, VISION, outbox, or journals as the feed.
3. At the verified pre-launch point, generate the snapshot into a newly created private per-pass workspace file using an atomic write; ensure the existing sandbox grants read-only access to that file only. Pass its path and schema to the planner as untrusted evidence, and require it to cite source times and state uncertainty. Do not broaden sandbox access to the runs directory, home, or environment. Delete the snapshot with the workspace after the pass.
4. Have the pinned change reviewed and updated through the Security GATES procedure, including wrapper/prompt/plist and sandbox pins where applicable. Test the actual launched planner with synthetic sentinel data: confirm it sees the snapshot, cannot read excluded files, and does not claim a merge or current main from missing/stale evidence. Separately integrate the immediate network reply if it should answer from the same validated projection; its current prompt is independent of the planner.
5. Roll out via the owning repository's sanctioned workflow and monitor source availability and freshness without logging payloads. Until this succeeds, reports must remain provisional.
