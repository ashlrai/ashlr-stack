Historical, unposted launch draft, revised against source 0.2.1. Recorded public npm 0.1.1 and historical native release 0.2.0 are separate artifacts; these examples do not establish that the source candidate is published or installed.

The source supports template setup, conditional SDK installation and provider switching. Each has prerequisites and partial-failure boundaries.

## What was broken and what we did about it

**Template setup.** `stack init --template X` writes the project configuration, then runs the selected template’s service setup unless `--noProvision` is supplied.

Example: `stack init --template nextjs-supabase-posthog` attempts the selected adapters with authorized provider accounts and a configured Phantom project. Supabase can create a project; PostHog accepts existing credentials. MCP descriptors are conditional. Stack does not fill `.env.local`, and failure can leave configuration or provider state to inspect.

**SDK installation.** `stack add` can offer the adapter’s SDK packages after setup. This is separate from provider and application readiness.

The default install mode asks in an interactive terminal and skips installation in a noninteractive one. Use the declared `--install always` or `--install never` mode when invoking `stack add` if you need an explicit choice.

**Package and runtime layers.** Publisher authentication is separate from consumer package installation. No npm OTP requirement for users is established by this source.

The recorded public npm 0.1.1 packages require Bun 1.2 or later. Reviewed source 0.2.1 and historical native 0.2.0 are distinct; check the actual installed version and help before applying source examples.

## What's new beyond the fixes

**Provider switching.** Inspect the planned target before changing local service configuration:

```bash
stack swap supabase neon --dryRun
```

The implemented swap sets up the target and then attempts old-service cleanup. It does not migrate application data, update every environment reference or rotate all credentials. Upstream resources remain; there is no registered `stack rollback` command. Inspect partial state and use supported recovery steps.

A dry run describes the proposed switch, not a completed migration or rollback guarantee.

**Telemetry controls.** Source includes opt-in telemetry and update checks. Review `stack telemetry` settings for the installed version; neither an install counter nor these source controls establish a blanket no-network or no-identifiers guarantee.

## How the provisioning pipeline works

`stack add supabase` coordinates these source phases. Their behavior depends on the selected adapter and installed prerequisites:

1. **Login.** Configured OAuth flows, PATs or API keys vary by adapter. Verification can be a remote probe or local structure check; it is not universal credential validity proof.
2. **Provision.** Supabase, Neon, Turso and Vercel have create-resource paths. Other adapters select existing resources or accept credentials; none of this creates every provider account.
3. **Materialize.** Managed credential values are passed to Phantom’s create-only stdin interface. Persistence can fail, and some critical credentials are committed before later setup steps. Conditional MCP descriptors are written as configuration, not launched.
4. **Persist.** Stack writes declarations and local instance metadata sequentially. Project-supplied metadata is not automatically secret-free or safe to commit; later failure can leave partial state.

`stack exec -- bun dev` forwards to the installed `phantom exec` interface. Stack does not itself resolve placeholders or produce a filled environment file. Qualify runtime credential delivery separately.

## 39 providers, same model

The source catalog has 39 entries. Examples include:

- **DB:** Supabase, Neon, Turso, Convex, Firebase
- **Deploy:** Vercel, Railway, Fly, Render, Cloudflare
- **Cloud:** AWS, GCP
- **AI:** OpenAI, Anthropic, xAI, DeepSeek
- **Obs:** Sentry, PostHog, Datadog, Grafana
- **Auth:** Clerk, Auth0
- **Payments:** Stripe
- **Infra:** Upstash, Resend
- **Dev:** GitHub, Linear

The registry contains 31 API-key factory adapters and eight custom adapters. Four custom adapters have resource-creation paths. OAuth prerequisites, returned slots and verification strength vary; a catalog entry is not live provider acceptance.

## Honest v0.2 caveats

This is an illustrative draft, not a posted announcement or customer acceptance record.

- **Source candidate.** Source behavior is not proof of a published package, installed runtime or working application.
- **Partial state.** Setup, credential persistence and configuration writes are sequential; cleanup is best effort.
- **Provider prerequisites.** Account permissions, existing organization or project requirements and configured OAuth apps vary by adapter.
- **Phantom is required for managed credentials.** Qualify its installed project and create-only credential interface separately.
- **Telemetry.** Source includes opt-in controls and update checks; do not infer zero telemetry or zero network contact.

## Roadmap

1. Qualify configured OAuth paths and account permissions for each adapter.
2. Record genuine provider acceptance before making runtime claims.
3. Improve errors around partial setup and recovery.
4. Evaluate team credential-sharing requirements against actual installed interfaces.
5. Extend the catalog only with qualified adapter contracts.
6. Qualify each supported platform separately; source checks do not establish Windows or WSL acceptance.
